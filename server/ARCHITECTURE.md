# AR Room — серверная часть

Документ, по которому можно писать бэкенд самому или отдать подрядчику. Описывает базу, API и — главное — как сделать экономику, которую нельзя обмануть.

---

## Зачем вообще сервер

Коллекция и монеты уже работают на телефоне. Сервер нужен ровно для трёх вещей, которые на клиенте сделать нельзя:

1. **Общая база** — чтобы карточки и балансы были одни на всех, а не у каждого свои.
2. **Обмен между людьми** — передать карточку другому игроку так, чтобы она пропала у одного и появилась у другого, и никто не смог задвоить.
3. **Защита от списывания** — пока баланс лежит на телефоне, любой человек с redsdk редактором открывает файл и ставит себе миллион монет. Как только за карточки платят (даже игровыми монетами) и обмениваются, источником правды обязан быть сервер.

Всё остальное (AR, съёмка, локальная коллекция) остаётся на клиенте и работает без сети.

---

## Золотое правило экономики

**Клиент никогда не сообщает серверу результат — только намерение.**

Неправильно: телефон говорит «начисли мне 500 монет за поимку легендарки». Тогда подделать запрос — дело пяти минут.

Правильно: телефон говорит «я поставил персонажа fox в комнату». Сервер сам смотрит, какая у fox редкость, первая это поимка или нет, и сам решает, сколько монет начислить. Клиент не участвует в расчёте награды и цены — он только присылает событие.

Это правило определяет весь дизайн API ниже.

## Модель данных

Реляционная БД (PostgreSQL). Ключевые таблицы:

### users
| поле | тип | заметки |
|---|---|---|
| id | uuid PK | |
| handle | text unique | ник для обмена, виден другим |
| created_at | timestamptz | |
| coins | bigint | **баланс живёт только здесь**, не на клиенте |

### characters
Каталог персонажей. Ведётся с сервера, клиент его кеширует.

| поле | тип | заметки |
|---|---|---|
| id | text PK | «fox», совпадает с id в клиенте |
| title | text | |
| model_url | text | ссылка на .glb |
| rarity | smallint | 0..3, **задаётся сервером**, не хэшем на клиенте |
| tradable | bool | можно ли обменивать |

> Важно: редкость переносится с клиентского хэша на серверное поле. Хэш был временным решением, чтобы редкость была стабильной без сервера. С появлением базы редкость становится настоящими данными, которые можно вручную настроить под баланс.

### inventory
Кто чем владеет. Одна строка на пару (пользователь, персонаж).

| поле | тип | заметки |
|---|---|---|
| user_id | uuid FK | |
| character_id | text FK | |
| count | int | сколько копий |
| first_caught_at | timestamptz | |
| favorite | bool | |
| PRIMARY KEY | (user_id, character_id) | |

### ledger
Журнал всех операций с монетами и карточками. **Только добавление, ничего не редактируется и не удаляется.** Это одновременно защита и возможность разобрать любой спор.

| поле | тип | заметки |
|---|---|---|
| id | uuid PK | |
| user_id | uuid | |
| kind | text | catch / buy / sell / trade_out / trade_in / purchase |
| character_id | text nullable | |
| coins_delta | bigint | +/− |
| ref | uuid nullable | id связанной сделки |
| created_at | timestamptz | |

### trades
Обмен между двумя игроками.

| поле | тип | заметки |
|---|---|---|
| id | uuid PK | |
| from_user | uuid | кто предложил |
| to_user | uuid | кому |
| offer_character | text | что отдаёт |
| request_character | text nullable | что хочет взамен (или монеты) |
| request_coins | bigint | |
| status | text | pending / accepted / declined / cancelled / expired |
| created_at, resolved_at | timestamptz | |

## API

REST, JSON, авторизация по токену в заголовке. Все изменяющие операции — идемпотентны по ключу запроса (см. ниже).

### Аутентификация
```
POST /auth/anonymous        → { user_id, token }   первый вход, аноним
POST /auth/link             привязать почту/Google к анонимному аккаунту
```
Начинаем с анонимного входа: человек ставит приложение и сразу играет, регистрация не нужна. Привязка аккаунта — когда захочет сохранить прогресс между устройствами.

### Каталог и профиль
```
GET  /catalog               → список characters (кешируется клиентом)
GET  /me                    → профиль, coins
GET  /me/inventory          → карточки игрока
```

### Игровые события (клиент шлёт намерение, не результат)
```
POST /events/catch          { character_id, idempotency_key }
     → сервер сам определяет редкость, первая ли поимка, начисляет монеты
     → { first_time, coins_awarded, new_balance }

POST /shop/buy              { character_id, idempotency_key }
     → сервер берёт цену из каталога, проверяет баланс, списывает
     → { success, new_balance }  либо 402 если не хватило

POST /shop/sell            { character_id, idempotency_key }
     → продать дубль, цена с сервера
```

### Обмен
```
POST /trades                { to_handle, offer_character, request_character?, request_coins? }
     → создаёт предложение, статус pending
GET  /trades                → входящие и исходящие
POST /trades/{id}/accept    → атомарно переносит карточки/монеты, пишет в ledger
POST /trades/{id}/decline
POST /trades/{id}/cancel
```

## Три защиты, без которых экономику сломают

### 1. Идемпотентность
Каждый изменяющий запрос несёт `idempotency_key` (uuid, генерит клиент). Сервер запоминает обработанные ключи. Если из-за плохой связи телефон отправит «поймал fox» дважды, второй запрос вернёт тот же результат, а не начислит монеты повторно. Без этого дубли запросов = бесплатные монеты.

### 2. Атомарность обмена
Принятие сделки — одна транзакция БД: у отправителя `count` уменьшается, у получателя увеличивается, монеты движутся, в ledger пишутся обе половины. Либо всё, либо ничего. Иначе при сбое посередине карточка либо задвоится, либо исчезнет.

Проверки внутри транзакции: у отправителя карточка ещё есть (не продал параллельно), у покупателя хватает монет, сделка ещё `pending` (не принята с другого устройства). Ставим блокировку строки (`SELECT ... FOR UPDATE`), чтобы две параллельные попытки не прошли обе.

### 3. Сервер считает сам
Повторю, потому что это главное: цена, награда, редкость — всё берётся из серверных таблиц. Клиент их присылать не может. Даже если злоумышленник полностью перепишет приложение, максимум, что он сделает — отправит «поймал легендарку», но легендарку ещё надо реально иметь в каталоге, а награду посчитает сервер.

## Античит по частоте

Поимка даёт монеты, значит найдётся тот, кто автоматизирует «поставил-убрал» тысячу раз. Меры:

- Награда за поимку конкретного персонажа — только первая. Повторные дают символический дубль-бонус (уже так в клиенте).
- Мягкий лимит: не больше N поимок в минуту с аккаунта, дальше монеты за поимку обнуляются до следующего окна.
- Аномалии видны по ledger постфактум — журнал для того и нужен.

## Стек, который я бы советовал

Не потому что единственный, а потому что дёшев на старте и не требует своих серверов:

- **База и API:** Supabase (управляемый Postgres + готовая авторизация + автогенерируемый REST). Обмен и начисления — в серверных функциях (Postgres RPC или Edge Functions), чтобы расчёт шёл на сервере, а не в приложении.
- **Файлы моделей:** любой S3-совместимый storage или тот же Supabase Storage, ссылки в `characters.model_url`.
- **Почему не Firebase:** его модель без строгих транзакций делает атомарный обмен заметно более хрупким. Для экономики реляционная база с транзакциями надёжнее.

Порядок реализации: сначала `/auth`, `/catalog`, `/me` — приложение начинает синхронизировать коллекцию. Потом `/events/catch` и магазин — экономика переезжает на сервер. Обмен — последним, он сложнее всего и требует, чтобы всё предыдущее уже работало.

## Что менять в клиенте

Почти ничего, и это не случайность. `CollectionRepository` уже написан так, что снаружи он — методы `catch/buy/sell` и потоки `wallet/owned`. Переход на сервер = переписать нутро этого одного класса на сетевые вызовы. Экраны коллекции, карточки, экономика UI не изменятся. Единственное новое в интерфейсе — экран обмена вместо нынешней заглушки и, возможно, экран входа при привязке аккаунта.
